- **Aucun paquet à vendorer pour le bureau.** Contrairement au Socle (`limine-snapper-sync`, `limine-mkinitcpio-hook` vendorés), le SP2 n'a **rien** à recompiler : la totalité de la pile bureau est servie par les dépôts officiels des deux architectures. `eschaton-desktop` peut être un pur meta-paquet `arch=(any)` de dépendances, conforme à la spec Socle §1.3.

## 3. Axe 2 — Documentation upstream des garanties

### 3.1 Le système de plugins DMS

**Anatomie d'un plugin** : un répertoire contenant `plugin.json` + des composants QML.

```json
{
  "id": "dankPomodoroTimer",          // camelCase, requis, unique
  "name": "Dank Pomodoro Timer",      // requis
  "version": "1.1.6",                 // requis
  "type": "widget",                   // widget | daemon | launcher | desktop | composite
  "component": "./DankPomodoroWidget.qml",
  "settings": "./DankPomodoroSettings.qml",
  "permissions": ["settings_read", "settings_write"],
  "requires_dms": ">=0.1.18"          // optionnel — contrainte de version DMS
}
```

- **Types de surface** (5) : `widget` (barre DankBar ou Control Center), `daemon` (service de fond, sans UI), `launcher` (extension du spotlight, avec `trigger`), `desktop` (widget de bureau), `composite` (plusieurs surfaces, `components` au lieu de `component`, **requiert DMS ≥ 1.5.0**).
- **Permissions** (4, déclaratives) : `settings_read`, `settings_write`, `process` (exécuter des commandes système), `network`.
- **Stabilité d'API** : **il n'y a pas de version d'API déclarée**. Le seul contrat est le champ `requires_dms` (contrainte semver sur la version de DMS). Les plugins importent directement les espaces de noms internes de DMS — `qs.Common`, `qs.Services`, `qs.Widgets`, `qs.Modules.Plugins` — et héritent de `PluginComponent`. **La surface d'extension est l'intérieur de DMS, pas une API figée.** Aucune promesse de compatibilité ascendante n'est publiée.
- **Chargement à chaud** : `PluginService.qml` pose un *folder watcher* sur les deux répertoires ; `dms ipc call plugins reload <id>` recharge sans redémarrer le shell.
- **Traductions** : un répertoire `translations/{fr,es,…}.json` à côté de `plugin.json` suffit, résolution en cascade plugin → catalogue DMS → anglais.

**Le point décisif pour Eschaton** — deux répertoires de plugins, aux régimes différents :

| | Répertoire | Régime | Verrouillage |
|---|---|---|---|
| Utilisateur | `~/.config/DankMaterialShell/plugins/` | clone git, `.repos/` interne | `plugins.lock.json` (commit git épinglé) |
| **Système** | **`/etc/xdg/quickshell/dms-plugins/`** | **lecture seule** — `cannot update system plugin` | **pacman** |

Le code branche explicitement sur le préfixe `/etc/xdg/quickshell/dms-plugins` pour interdire update et suppression par le gestionnaire de plugins. C'est le point d'ancrage exact du principe *fat packages* : un paquet `eschaton-dms-plugin-foo` dépose `/etc/xdg/quickshell/dms-plugins/foo/{plugin.json,*.qml}`, et DMS le charge sans jamais chercher à le muter. **Le `plugins.lock.json` cité par l'ADR est donc hors sujet pour nos plugins** : c'est pacman qui joue son rôle, et c'est mieux ainsi.

Sources : [`core/internal/plugins/manager.go`](https://github.com/AvengeMedia/DankMaterialShell/blob/master/core/internal/plugins/manager.go), [`quickshell/Services/PluginService.qml`](https://github.com/AvengeMedia/DankMaterialShell/blob/master/quickshell/Services/PluginService.qml), [doc plugin-development](https://github.com/AvengeMedia/DankLinux-Docs/blob/main/docs/dankmaterialshell/plugin-development.mdx) (versionnée : `versioned_docs/version-1.5/`), [CONTRIBUTING du registre](https://github.com/AvengeMedia/dms-plugin-registry/blob/main/CONTRIBUTING.md).

### 3.2 Multi-compositeur : ce que « supporté » veut dire

Support complet (workspaces, overview, gestion des moniteurs) : **niri, Hyprland, sway, MangoWC, labwc, Scroll, MiracleWM**. Les autres compositeurs Wayland fonctionnent « avec des fonctions réduites ». Mécaniquement, le paquet `dms-shell` dépend du virtuel `dms-shell-compositor`, fourni par `dms-shell-hyprland` ou `dms-shell-niri` — donc changer de compositeur est un changement de dépendance de meta-paquet, pas une réécriture. Le verrou technique est faible ; **le verrou réel est la configuration** (`~/.config/hypr/dms/*.lua` est spécifique à Hyprland).

Signal à noter : le profil officiel archinstall 4.4 est **niri + DMS**, et c'est le lead DMS qui l'a contribué. L'upstream considère niri comme sa cible de référence.

### 3.3 `hyprland.lua` — la déprécation d'hyprlang

- **Upstream Hyprland** : Lua disponible depuis 0.55 ; hyprlang supporté « 1 à 2 releases à partir de 0.55 », puis **abandonné**. Aucune date ferme. 0.56.0 (2026-07-20) annonce *« No breaking changes! :) »* — hyprlang y fonctionne encore — mais la release contient une vingtaine d'entrées `config/lua` : tout le développement de configuration se fait désormais en Lua.
- **Cadence Hyprland** : 0.54.0 = 2026-02-27, 0.55.0 = 2026-05-09, 0.56.0 = 2026-07-20 → une mineure tous les ~2,4 mois. **0.57 est attendue vers fin septembre / octobre 2026**, et c'est la fenêtre de suppression annoncée d'hyprlang.
- **Côté DMS** : `dms setup` déploie un arbre Lua complet (`hyprland.lua` + `dms/{colors,outputs,layout,cursor,binds,binds-user,windowrules}.lua`), sauvegarde les `.conf` hérités dans `~/.config/hypr/.dms-backups/<timestamp>/`, et migre les lignes `monitor = …`.
- **Contrainte de lancement, non triviale** : la config Lua n'est active que si Hyprland est démarré avec **`Hyprland -c ~/.config/hypr/hyprland.lua`**. Sinon Hyprland auto-génère un `hyprland.conf` et ignore le Lua. L'entrée de session / desktop entry doit porter ce drapeau. C'est un invariant à packager et à vérifier, exactement comme l'invariant de nommage d'OS du Socle.
- **Frontière de propriété déclarée par DMS** : *« Binds from your own `hyprland.lua` (outside the `dms/` folder) are read-only in Settings — DMS does not write into files it does not manage. »* DMS s'engage donc à ne toucher que `~/.config/hypr/dms/`. En revanche `dms/binds.lua` est **réécrit par `dms setup`** ; les surcharges vont dans `dms/binds-user.lua`.

Sources : [hypr.land/news/26_lua](https://hypr.land/news/26_lua/), [notes 0.56.0](https://github.com/hyprwm/Hyprland/releases/tag/v0.56.0), [Hyprland_Lua_Migration.md](https://github.com/AvengeMedia/DankMaterialShell/blob/master/docs/Hyprland_Lua_Migration.md).

## 5. Axe 4 — Le point aarch64 : **le facteur limitant n'existe pas**

L'ADR 0001 §5 marque l'aarch64 comme « possiblement le vrai facteur limitant, avant toute considération de design ». **Ce risque est levé.**

### 5.1 Preuves

1. **Binaires natifs aarch64 déjà publiés par ALARM** (index miroir, horodatages du miroir) :

   ```
   quickshell-0.3.1-1-aarch64.pkg.tar.xz            21-Aug-2026 16:04
   dms-shell-1.5.3-1-aarch64.pkg.tar.xz             27-Jul-2026 10:32
   dms-shell-hyprland-1.5.3-1-aarch64.pkg.tar.xz    27-Jul-2026
   dms-shell-niri-1.5.3-1-aarch64.pkg.tar.xz        27-Jul-2026
   dgop-0.2.3-1-aarch64.pkg.tar.xz                  29-Jun-2026 18:17
   hyprland-0.56.1-3-aarch64.pkg.tar.xz             01-Aug-2026 13:26
   qt6-base-6.11.2-2-aarch64.pkg.tar.xz             20-Aug-2026 11:45
   qt6-declarative-6.11.2-1-aarch64.pkg.tar.xz      20-Aug-2026 14:21
   ```

   Ce ne sont pas des paquets `any` : le suffixe `-aarch64` atteste d'une compilation native par le *Arch Linux ARM Build System*.

2. **CI upstream multi-architecture** : `.github/workflows/release.yml` de DMS a une matrice `{linux, freebsd} × {amd64, arm64}` (`GOOS`/`GOARCH`) et publie à chaque release **`dms-full-arm64.tar.gz`** — « Complete package for ARM64 systems (CLI binaries + QML source + shell completions) ». L'arm64 est une cible de première classe, pas un accident.

3. **Aucune issue bloquante aarch64** : recherche d'issues `aarch64 OR arm64` — Quickshell : 3 résultats, tous sans rapport (crashs IPC). DMS : 24 résultats, dont aucun blocage de compilation ou d'exécution sur ARM. Les seuls sujets ARM réels sont périphériques et **Apple Silicon**, pas ARM en général : [#2061](https://github.com/AvengeMedia/DankMaterialShell/issues/2061) « Night mode: software overlay fallback when hardware gamma is unavailable (Apple Silicon/Asahi) » (ouverte 2026-03-23) et [#2016](https://github.com/AvengeMedia/DankMaterialShell/issues/2016) (encoche MacBook).

4. **Qt6 sur ALARM** : `qt6-base 6.11.2-2`, `qt6-declarative`, `qt6-wayland`, `qt6-svg`, `qt6-multimedia`, `qt6-shadertools` tous en **6.11.2**, tous construits le 2026-08-20, tous **strictement identiques à Arch x86_64**. Le minimum Quickshell est Qt 6.6.

### 5.2 Effort de packaging par architecture — réestimé

| | Estimation ADR 0001 | Estimation 2026-08-28 |
|---|---|---|
| Quickshell aarch64 | à compiler sur le banc d'essai | **0** — `pacman -S quickshell` |
| DMS (daemon Go + QML) aarch64 | à compiler sur le banc d'essai | **0** — `pacman -S dms-shell dms-shell-hyprland` |
| `eschaton-desktop` | meta-paquet | meta-paquet `arch=(any)`, **liste de dépendances identique sur les deux architectures** |
| `eschaton-dms-plugin-*` | QML pur | QML + JSON → `arch=(any)`, **une seule construction pour les deux architectures** |

**L'écriture `arch=(any)` de la spec Socle §1.3 tient pour tout le SP2.** Aucune branche par architecture n'est nécessaire dans les PKGBUILDs du bureau. La seule divergence connue est `hyprland` 0.56.2 (x86_64) contre 0.56.1 (aarch64) — un décalage de version corrective, pas d'API.

### 5.3 Réserves honnêtes

- Le fait qu'un paquet existe ne prouve pas qu'il **tourne** : rien ne remplace le lancement de DMS dans la VM UTM. Le rendu QtQuick sous `virtio-gpu` en VM ARM (accélération, `libglvnd`/`mesa`) est le seul inconnu sérieux restant, et il relève du **banc d'essai**, pas de l'architecture.
- Le *night mode* de DMS s'appuie sur le gamma matériel ; en VM (comme sur Asahi) il est probable qu'il soit inopérant tant que [#2061](https://github.com/AvengeMedia/DankMaterialShell/issues/2061) n'est pas résolue.
- `hyprland` sur ALARM est bâti pour aarch64 générique ; la réserve « ARMv8.2-A minimum » de la spec Socle §8.1 concerne Arch Linux Ports, pas ALARM.

## 6. Axe 5 — Paysage concurrent : le différenciateur zéro-terminal

### 6.1 Existe-t-il déjà une distro Arch pilotable en GUI de bout en bout ?

**Pas exactement — mais toutes les briques existent chez les concurrents, et plusieurs les assemblent déjà largement.**

| Distro | Paquets en GUI | Mises à jour en GUI | Snapshots / rollback en GUI | Réglages système en GUI | Verdict |

### 6.2 Le différenciateur tient-il ?

**Non, pas tel qu'il est formulé.** « Une distro Arch pilotable en GUI de bout en bout » ne décrit plus un territoire vide au 2026-08-28 :

- **Omarchy 4 a fermé l'écart le plus important** : paquets Arch et AUR installables/supprimables graphiquement, depuis un menu intégré au shell Quickshell. C'est précisément ce que la spec du Socle §1 lui déniait. La note de veille du 2026-08-27 avait vu qu'Omarchy 4 supprimait « Hyprland + Quickshell » et « IA intégrée » comme différenciateurs ; **elle n'a pas vu qu'il entamait aussi le zéro-terminal**.
- **Omarchy 4 a aussi adopté le principe *fat packages*** : *« Re-architect Omarchy into proper Arch packages with system files shipped via `/etc`, so updates flow through pacman »*, avec une frontière dure `/usr/share/omarchy/` (au paquet) contre `~/.config/` (à l'utilisateur). C'est le principe directeur de la spec Socle §3, déjà implémenté par un concurrent.
- **Omarchy 4 a un système de plugins de barre** : `omarchy plugin add <git-url>`. Le modèle d'extension n'est plus discriminant non plus.

**Ce qui reste réellement vide** — et qui devrait devenir la formulation du différenciateur :

1. **Le rollback graphique complet.** Personne, sur base Arch, n'offre « parcourir les snapshots, comparer, restaurer » comme une fonction de première classe **du shell**. Omarchy s'arrête à la réinitialisation d'usine ; CachyOS et Garuda délèguent à `btrfs-assistant` / Timeshift, applications tierces hors du bureau. C'est le seul terrain où Eschaton peut être premier.
2. **L'unité.** Chez les concurrents, le zéro-terminal est un patchwork d'applications hétérogènes (pamac en GTK, btrfs-assistant en Qt, Garuda Assistant à part, Shelly à part) posées à côté du bureau. Personne ne l'a fait **dans le shell**, avec une seule identité visuelle et un seul modèle d'interaction. Le modèle de plugins DMS rend exactement cela possible.
3. **La combinaison** rollback graphique + assistant IA systémique + bureau moderne cohérent. Aucune brique n'est inédite ; l'assemblage l'est.

## 7. Conséquences pour la spec SP2

### 7.1 Ce que la veille **impose**

1. **Corriger l'ADR 0001 avant d'écrire la spec** (ADR 0002 §2 : « tout constat de terrain contredisant la spec remonte dans la spec »). Trois corrections :
   - §1, tableau : licence DMS = **MIT**, pas GPL-3.0 ; packaging = **`extra` (Arch officiel)**, pas AUR.
   - §5 : supprimer « ni Quickshell ni DMS n'ont de binaires ALARM ; tout se compile sur le banc d'essai » — **faux**, et faux au moment de la rédaction.
   - §3, récolte n°2 : l'épinglage de Quickshell à un commit n'a plus lieu d'être, Quickshell étant en dépôt officiel avec des releases taguées.
2. **Reformuler le différenciateur dans la spec du Socle §1.** « Pilotable en GUI de bout en bout » ne décrit plus un territoire vide (Omarchy 4 installe et supprime des paquets en GUI). La formulation défendable au 2026-08-28 : **« le rollback et la gestion de paquets comme fonctions natives et unifiées du shell, pas comme applications tierces juxtaposées »**.
3. **Packager la configuration Hyprland en Lua uniquement**, et packager **l'invariant de lancement** `Hyprland -c ~/.config/hypr/hyprland.lua` dans l'entrée de session. Sans ce drapeau, Hyprland auto-génère un `hyprland.conf` et la config Lua est silencieusement ignorée — même famille de panne que les ruptures silencieuses de §8 du Socle.
4. **Trancher explicitement la propriété de `~/.config/hypr/`.** `dms setup` réécrit `~/.config/hypr/dms/*.lua`. Un paquet Eschaton qui y déposerait des fichiers serait écrasé. La spec doit choisir et écrire son choix : soit `dms setup` reste maître de `dms/` et Eschaton n'écrit que `hyprland.lua` + `dms/binds-user.lua`, soit Eschaton n'appelle jamais `dms setup` et possède tout l'arbre. **Recommandation : la première** — elle respecte la frontière déclarée par l'upstream (« DMS does not write into files it does not manage ») et évite de reprendre à la main une migration Lua qui bouge encore.
5. **Épingler les versions par le dépôt, pas par des commits git.** `eschaton-desktop` déclare des dépendances versionnées vers `extra`/ALARM. Aucun `-git`, aucun vendoring, aucun `PKGBUILD` recompilant Quickshell.

### 7.2 Ce que la veille **interdit**

- **Interdit de recompiler Quickshell ou DMS.** C'est du travail pour rien sur les deux architectures.
- **Interdit de faire dépendre les plugins Eschaton du mécanisme `plugins.lock.json`** : c'est le chemin des plugins utilisateur installés par git. Nos plugins passent par `/etc/xdg/quickshell/dms-plugins/`, possédés par pacman, traités en lecture seule par DMS.
- **Interdit de bâtir la gestion de paquets sur PackageKit** (backend alpm rudimentaire, retiré de GNOME Software côté Arch).
- **Interdit de dépendre de `pamac`, `octopi` ou `shelly`** : absents des dépôts officiels et **absents d'ALARM** — ils casseraient le banc d'essai quotidien.
- **Interdit d'ajouter `timeshift`** à côté de Snapper : deux filets de sécurité concurrents en valent zéro.

### 7.3 Ce que la veille **recommande**

- **Livrer `btrfs-assistant` dès la v1 du bureau** comme dépendance de `eschaton-desktop`. Il est dans `extra`, en version identique sur les deux architectures, et rend le rollback graphique disponible immédiatement. Il sera remplacé par un panneau natif quand celui-ci existera — c'est une **dette assumée avec condition de sortie explicite** (ADR 0002 §2), pas un renoncement.
- **Viser les types de plugin `daemon` et `composite`, pas seulement `widget`.** Le critère n°1 de passage au shell maison (ADR 0001 §4 — « l'assistant IA omniprésent déborde d'un widget de barre ») repose sur une vision trop étroite du modèle : DMS offre `daemon` (service de fond), `launcher` (extension du spotlight, avec `trigger`) et `composite` (plusieurs surfaces, DMS ≥ 1.5.0), plus une permission `process`. Un assistant systémique tient dans ce modèle. **Ce critère devrait être révisé à la baisse dans l'ADR 0001.**
- **Ne pas fermer la porte à niri.** Le profil officiel archinstall est niri + DMS, `dms-shell-niri` est un simple fournisseur alternatif de `dms-shell-compositor`, et niri est en version identique sur les deux architectures. Structurer `eschaton-desktop` pour que le compositeur soit une dépendance substituable, et non un choix diffusé dans toute la configuration.
- **Fixer la politique de version DMS.** `master` a 444 commits d'avance sur `v1.5.3` (32 jours). Suivre `extra/dms-shell` et rien d'autre ; déclarer `requires_dms` dans chaque `plugin.json` Eschaton ; ajouter au CI une vérification que la version d'`extra` satisfait toujours nos contraintes.
- **Écrire un test de non-régression aarch64/x86_64 dès le premier paquet** : `eschaton-desktop` étant `arch=(any)` avec la même liste de dépendances, la seule chose à vérifier est que ces dépendances **existent aux deux endroits**. Un script qui interroge les deux index de dépôts suffit et coûte peu.
- **Mesurer avant de conclure sur l'ergonomie.** Les jugements d'ergonomie et d'empreinte mémoire de l'ADR 0001 restent des jugements tiers. La première tâche du SP2 demeure : installer DMS dans la VM UTM aarch64 et confronter l'ADR au réel.

## 8. Risques

*Table établie le 2026-08-28 (passe de veille SP2, [ADR 0002](../../../docs/decisions/0002-veille-avant-spec.md)).*

| # | Risque / question | Traitement |
|---|---|---|
| 1 | ~~Quickshell et DMS non disponibles sur aarch64, tout à compiler~~ | **Levé le 2026-08-28.** `quickshell 0.3.1-1`, `dms-shell 1.5.3-1`, `dms-shell-{hyprland,niri}`, `dgop 0.2.3-1` sont publiés en binaires **natifs aarch64** dans ALARM `extra`, aux mêmes versions qu'Arch x86_64 ; la CI upstream de DMS publie `dms-full-arm64.tar.gz`. Effort de packaging par architecture : **nul**. |
| 2 | **Suppression d'`hyprlang` par Hyprland** | Upstream : hyprlang tenu « 1 à 2 releases à partir de 0.55 », puis abandonné. 0.56 est passée sans casse ; **0.57 (≈ octobre 2026) est la fenêtre**. Traitement : configuration **Lua exclusivement** dès le premier paquet, plus l'invariant de lancement `-c ~/.config/hypr/hyprland.lua` packagé dans l'entrée de session. Surveiller les notes de 0.57. |
| 3 | **Conflit de propriété sur `~/.config/hypr/`** entre `dms setup` et les paquets Eschaton | `dms setup` réécrit `~/.config/hypr/dms/*.lua` sans préavis ; un fichier Eschaton posé là serait écrasé silencieusement. Traitement : la spec tranche la frontière (recommandation §7.1.4 — DMS garde `dms/`, Eschaton prend `hyprland.lua` et `dms/binds-user.lua`) et un test vérifie qu'un `dms setup` ne détruit pas la configuration Eschaton. |
| 4 | **API de plugins DMS non versionnée** | Aucune version d'API n'est publiée ; les plugins importent les internes de DMS (`qs.Common`, `qs.Services`, `qs.Widgets`) et héritent de `PluginComponent`. Une refonte interne casse les plugins sans avertissement. Atténuations : le champ `requires_dms` permet de déclarer une contrainte semver ; la docs est versionnée (1.2/1.4/1.5) ; les 12 plugins first-party servent de canari — s'ils cassent, l'upstream le voit. Traitement : `requires_dms` obligatoire sur tout `eschaton-dms-plugin-*`, et un smoke test de chargement des plugins dans le CI. |
| 5 | **Bus factor de Quickshell = 1** | `outfoxxed` porte 781 commits sur ~810 ; projet en 0.x avec breaking changes annoncés avant 1.0. Atténuation réelle : Quickshell est dans `extra` (Arch prend en charge la continuité d'empaquetage) et le lead DMS en est le contributeur n°2. Traitement : surveillance ; c'est le déclencheur le plus probable du critère n°4 de l'ADR 0001. |
| 6 | **Jeunesse et concentration de DMS** | Dépôt créé le 2025-07-10 (13 mois) ; `bbedward` 2 852 commits, `purian23` 718, puis chute brutale. Contrepoids : 7 776 étoiles, 487 forks, MIT (donc forkable sans obstacle), entrée dans Arch `extra` et dans archinstall, écosystème de 10 dépôts actifs, empaquetages Fedora/openSUSE/Ubuntu/Void/Nix soutenus par la CI. Traitement : rester sur l'option A, garder les critères de passage à C de l'ADR 0001 §4, réviser le critère n°1 (trop pessimiste — voir §7.3). |
| 7 | **Retard de `hyprland` sur ALARM** | 0.56.1-3 (ALARM) contre 0.56.2-1 (Arch) — ~3 semaines. Seul écart de version observé sur 13 paquets. Sans conséquence aujourd'hui ; deviendra critique quand 0.57 supprimera hyprlang, si ALARM traîne à ce moment-là. Traitement : intégrer `hyprland` à la surveillance ALARM déjà instaurée par le risque n°2 de la spec du Socle. |
| 8 | **Érosion du différenciateur zéro-terminal** | Omarchy 4 (2026-08-14) installe/supprime paquets Arch et AUR en GUI, a adopté le modèle *fat packages* et un système de plugins ; CachyOS livre un gestionnaire GUI par défaut ; Manjaro et Garuda couvrent le terrain depuis des années. **La formulation actuelle du différenciateur (spec Socle §1) est périmée.** Traitement : reformuler autour du rollback graphique natif et de l'unité dans le shell (§6.2), et **rejouer cette veille à l'ouverture du SP3 et du SP4** — c'est l'affirmation la plus volatile du projet. |
| 9 | **Écart entre `extra/dms-shell` et `master`** | 444 commits / 32 jours d'écart. Une fonction observée sur `master` ou dans la documentation peut ne pas être dans le paquet installé. Traitement : ne juger que sur la version d'`extra` ; le premier test en VM se fait sur `extra/dms-shell 1.5.3-1`, jamais sur `dms-shell-git`. |
| 10 | **Rendu QtQuick en VM UTM aarch64** | Seul inconnu technique réel restant : accélération `virtio-gpu`, `mesa`/`libglvnd` sous Wayland en VM ARM. Non documenté par l'upstream. Traitement : c'est l'objet du premier spike du SP2 ; à traiter avant toute décision de design. |
| 11 | **`night mode` de DMS inopérant en VM** | DMS s'appuie sur le gamma matériel ; issue upstream ouverte [#2061](https://github.com/AvengeMedia/DankMaterialShell/issues/2061) demandant une bascule logicielle pour Apple Silicon/Asahi. Probablement inopérant en VM UTM. Traitement : ne pas compter cette fonction dans les critères d'acceptation du SP2 tant que le test réel n'a pas tranché. |
