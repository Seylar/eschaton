# Veille datée — Installer Eschaton (Arch Linux) sur un MacBook Pro 2019 (puce T2)

- **Date de la passe** : 2026-08-29
- **Machine confirmée** : **MacBook Pro i7, 2019, 16 Go de RAM**. → **Tous les MacBook Pro 2019 embarquent la puce T2.** La branche « sans T2 » de la veille précédente est abandonnée : tout ce rapport traite du **cas T2**.
- **Contrainte de méthode (ADR 0002 « veille datée avant spec »)** : chaque affirmation porte sa source et sa date/version. Là où 2026 reste incertain, c'est écrit explicitement.
- **Repères de version 2026** : mainline Linux **7.1.5** (ISO Arch officielle 2026.08.01, linuxcompatible.org, 2026-08-01) ; ISO `archiso-t2` la plus récente : **2026.03.07** (github.com/t2linux/archiso-t2/releases).

> ⚠️ **Trois faits structurants, à lire avant tout le reste :**
> 1. **Touch ID est INUTILISABLE sous Linux** (raison architecturale, pas un manque de pilote temporaire — §4). L'idée de remplacer le mot de passe par l'empreinte sur ce Mac est **un cul-de-sac**.
> 2. **Le disque interne est piloté par la T2** : sans noyau patché, l'installeur **ne voit aucun disque** (§6). Une ISO Arch/Eschaton standard échoue avant même de partitionner.
> 3. **Il faut un noyau aval tiers (`linux-t2`) qui suit mainline avec du retard** : pour une distro à **mises à jour continues + rollback sur snapshot** comme la nôtre, c'est le risque n°1 (§2).

## 0. Verdict express

1. **Ce Mac est faisable sous Arch/t2linux, mais c'est un cas atypique et fragile**, à l'opposé du matériel grand public visé par Eschaton. Bon pour le dogfooding de Seylar ; mauvais pour juger le produit « pour les autres » (§9).
2. **Sous-question restante (seule chose encore à préciser)** : **quel modèle 2019 exactement ?** 13″, 15″ ou 16″ ? Cela change UNE chose importante : la présence d'un **GPU AMD discret** (15″/16″) qui demande une gestion hybride, vs le 13″ (iGPU seul, plus simple). Voir §1.2 et l'arbre ci-dessous.
3. **Frontal avec notre doctrine** : `linux-t2` est un noyau `x86_64` + dépôt tiers `SigLevel = Never` ; c'est incompatible avec « paquets `arch=(any)`, pas de migrations ». À trancher au niveau ADR, pas dans un PKGBUILD (§9).
4. **Reco banc d'essai** : **effacer tout le disque** (pas de double-boot macOS) — après avoir baissé le Secure Boot en Recovery. Élimine APFS/EFI partagé et les MAJ macOS qui cassent le boot (§6, §8).

## 1. Confirmation T2 et ce que la puce contrôle

### 1.1 T2 = certitude sur un MBP 2019
Apple : les MacBook Pro « introduits de 2018 à 2020 » embarquent la T2 (support.apple.com/en-us/103265, consulté 2026-08-29). Un MBP 2019 en fait partie sans exception. URL : https://support.apple.com/en-us/103265

### 1.2 La T2 est le contrôleur de presque tout le châssis
La T2 est un SoC ARMv8 qui exécute **bridgeOS** et intègre : le **contrôleur de stockage** (SSD), la Secure Enclave (Touch ID, chiffrement), le SMC (ventilateurs/capteurs), l'audio, la webcam, le clavier/trackpad (via BCE). Source : appleinsider / TechCrunch (Secure Enclave dans la T2), Macworld *« How FileVault and the T2… work together »*. URL : https://www.macworld.com/article/234494/how-filevault-and-the-t2-security-chip-work-together-in-newer-macs.html

Conséquence : **rien de tout ça n'est visible par un noyau Linux standard**. Il faut la pile **`apple-bce`** (Buffer Copy Engine) qui expose clavier/trackpad/audio/webcam, plus les correctifs NVMe.

### 1.3 Spécificité 2019 par taille d'écran
- **13″ 2019** (MacBookPro15,2 « 4 ports » / 15,4 « 2 ports ») : **iGPU Intel Iris Plus uniquement** → pas de bascule GPU, cas le plus simple.
- **15″ 2019** (MacBookPro15,1/15,3) : iGPU **+ AMD Radeon Pro 555X/560X/Vega 16/20**.
- **16″ 2019** (MacBookPro16,1) : i7-9750H ou i9, iGPU **+ AMD Radeon Pro 5300M/5500M** (option 5600M). Source specs : support.apple.com/en-us/111932 ; Geekbench MacBookPro16,1. URL : https://support.apple.com/en-us/111932
- **dGPU AMD sous Linux** : géré (`amdgpu`) mais demande une **gestion hybride** (script `gpu-switcher`, `apple-gmux force_igd=y`, dGPU bridée par défaut). **La Radeon Pro 5600M (HBM2) donne un écran noir au boot** et exige `nomodeset`/contournements (rapport LKML *« AMD Radeon Pro 5600M… blank screen on Linux »*). Sources : guide *fedora-macbook-pro-2019-16* (github.com/g-r-3-y/…, consulté 2026-08-29) ; LKML. URL : https://github.com/g-r-3-y/fedora-macbook-pro-2019-16

## 2. État réel de t2linux en 2026 pour un MBP 2019 — et le RISQUE de cadence noyau

### 2.1 Oui, un noyau patché reste obligatoire en 2026
- **`linux-mbp` est abandonné** ; la reco est **`linux-t2`** (ou `linux-xanmod-edge-t2`). Le noyau Arch T2 est maintenu dans un dépôt tiers : **`NoaHimesaka1873/linux-t2-arch`** (« Kernel for T2 Macs — Under New Management! »). URL : https://github.com/NoaHimesaka1873/linux-t2-arch
- Une **partie** du support est remontée upstream (contrôleur NVMe dès le **5.4**, capteur de luminosité + Touch Bar en **6.15**), **mais le cœur `apple-bce` (clavier/trackpad/audio/USB) reste hors-arbre** au 2026-08-29. Source : t2linux wiki *State* (wiki.t2linux.org/state/). URL : https://wiki.t2linux.org/state/
- Recette Arch (dépôt + paquets + params) : `linux-t2`, `linux-t2-headers`, `apple-t2-audio-config`, `apple-bcm-firmware`, `t2fanrd`, params `intel_iommu=on iommu=pt pm_async=off`. Dépôt `[arch-mact2]` avec **`SigLevel = Never`**. Source : wiki.t2linux.org/distributions/arch/installation/. URL : https://wiki.t2linux.org/distributions/arch/installation/

### 2.2 Le dépôt suit mainline **avec retard** — le point critique pour NOUS
- `linux-t2` est un **paquet distinct** de `linux`, publié par **un seul mainteneur** sur un **mirror tiers** (`mirror.funami.tech/arch-mact2`). Quand mainline avance (ex. 7.1.5 début août 2026), le paquet T2 doit être **reconstruit et republié** : il existe une **fenêtre de décalage** structurelle. Source (mécanique du dépôt/mirror) : NoaHimesaka1873/apple-bcm-firmware & arch-mact2 ; guide Matt Gibson (mattgibson.ca, install Arch T2). URLs : https://github.com/NoaHimesaka1873/apple-bcm-firmware · https://mattgibson.ca/installing-arch-linux-on-an-intel-macbook-pro-with-t2-security-chip/
- **Symptôme documenté** : sur un fil Arch dédié, à la question « si pacman installe un nouveau noyau, ça casse mon install ? », la réponse est **« Yupp you most likely will! »** ; les utilisateurs **sélectionnent manuellement le noyau T2 au boot**, et un intervenant qualifie **Touch ID et (à l'époque) l'audio de « unsolvable problems »**. Source : bbs.archlinux.org/viewtopic.php?id=299034 (consulté 2026-08-29). URL : https://bbs.archlinux.org/viewtopic.php?id=299034

### 2.3 Ce que ça implique pour une distro à MAJ continues + rollback snapshot (analyse)
- **Scénario de brique** : une mise à jour tire (par dépendance ou erreur de config) le noyau **stock `linux`** au lieu de `linux-t2`, **ou** l'utilisateur démarre la mauvaise entrée Limine → **plus de clavier, ni trackpad, ni disque visible** = machine inutilisable tant qu'on ne rebascule pas.
- **Notre garde-fou (Btrfs + snapper + Limine) est pertinent mais à double tranchant** : le rollback sur snapshot restaure un noyau qui marche (bien) — mais le fait même qu'on en ait besoin prouve que **les updates sont plus risquées ici que sur matériel générique**.
- **Recommandations concrètes** (à porter dans SP4b) :
  - **Ne jamais installer `linux` sur cette machine** ; épingler `linux-t2` comme unique noyau.
  - Envisager `IgnorePkg`/hook pacman qui **bloque un `-Syu` si `linux-t2` n'est pas disponible pour la version cible** (évite le décalage dangereux). *À concevoir — non fourni par t2linux.*
  - **Toujours prendre un snapshot pré-update** et garder une **entrée Limine de secours** vers le dernier noyau T2 connu bon.
  - Garder une **clé USB `archiso-t2`** de dépannage (elle, voit le disque). URL : https://github.com/t2linux/archiso-t2/releases/tag/2026.03.07

## 4. Touch ID sous Linux — réponse définitive : **NON, et ce n'est pas un simple manque de pilote**

> **C'est la réponse la plus importante de cette passe pour votre projet** : vous cherchez à remplacer la saisie de mot de passe par une auth graphique. **Sur ce Mac, Touch ID ne peut PAS jouer ce rôle sous Linux.**

### 4.1 Les faits sourcés
1. **Aucun support côté t2linux** : la page *State* (référence du projet) **ne liste aucun composant « empreinte / Touch ID »** parmi le matériel géré. Absence = non supporté. URL : https://wiki.t2linux.org/state/
2. **Déclaré « unsolvable » par la communauté Arch T2** (fil dédié) : Touch ID cité comme problème non résolu, distinct des autres. URL : https://bbs.archlinux.org/viewtopic.php?id=299034
3. **Aucun pilote ni module PAM ne cible ce capteur** : les projets de rétro-ingénierie d'empreintes sous Linux visent des lecteurs USB **Validity/Synaptics/Goodix** de PC (ex. `Validity90`, drivers `libfprint` communautaires) — **pas** le capteur Apple de la T2. Sources : github.com/nmikhailov/Validity90 ; hub `libfprint` communautaire. URL : https://github.com/nmikhailov/Validity90

### 4.2 Pourquoi c'est structurel (pas temporaire)
Le capteur d'empreinte des Mac T2 **n'envoie pas l'image au système d'exploitation**. Il est câblé à la **Secure Enclave** interne à la T2 ; l'empreinte est comparée **dans** l'enclave, qui ne renvoie qu'un déverrouillage de secret sous conditions. Or `libfprint`/`fprintd` (la pile Linux) attend soit l'image brute, soit un verdict « match/no-match » exploitable — **deux choses que l'architecture T2 ne fournit pas** à un OS tiers. Apple ne documente pas d'API pour bridgeOS. Source (explication de l'architecture Secure Enclave vs fprint) : Matthew Garrett, *« Why does Gnome fingerprint unlock not unlock the keyring? »* (mjg59.dreamwidth.org) ; TechCrunch/Apple sur la Secure Enclave dans la T2. URLs : https://mjg59.dreamwidth.org/68537.html · https://support.apple.com/en-us/105095

### 4.3 Conséquence pour Eschaton
- **Ni session, ni `sudo`, ni modale polkit ne peuvent être déverrouillés par Touch ID** sous Linux sur ce matériel. À dire **nettement** à l'utilisateur : ce n'est pas « pas encore », c'est « pas possible » sur T2.
- Notre objectif « remplacer le mot de passe par une auth graphique » doit donc reposer sur **autre chose** : agent polkit graphique classique (saisie mot de passe), ou facteur **externe** (clé FIDO2/U2F USB via `pam-u2f`, YubiKey, ou lecteur d'empreinte USB tiers supporté par `fprintd`). **Aucune de ces options n'utilise le capteur intégré du Mac.**

## 5. Wi-Fi/Bluetooth Broadcom sur T2 — et l'impact direct sur l'installeur

### 5.1 Le bon pilote et le firmware
- **`brcmfmac`** est le **seul** pilote correct (le wiki interdit explicitement `broadcom-wl` sur T2). URL : https://wiki.t2linux.org/guides/wifi-bluetooth/
- Le firmware provient de **macOS** — mais **bonne nouvelle** : il est **pré-empaqueté**. Le paquet **`apple-bcm-firmware`** (« Wi-Fi and Bluetooth Firmware from macOS Big Sur for T2 and M1 Macs ») est en version **14.0**, **`arch=(any)`**, et **contient les fichiers firmware**. Sur Arch/EndeavourOS, une fois `apple-bcm-firmware` installé, **aucune extraction manuelle** n'est nécessaire (exceptions : iMac19,1/19,2, iMacPro1,1 — **pas** un MBP 2019). Source : github.com/NoaHimesaka1873/apple-bcm-firmware ; wiki wifi-bluetooth. URL : https://github.com/NoaHimesaka1873/apple-bcm-firmware

### 5.2 Réponse à la question « une install propre a-t-elle du réseau ? »
- **OUI, si notre ISO embarque `apple-bcm-firmware`** (comme le fait `archiso-t2`) : le Wi-Fi fonctionne au premier boot **sans passer par macOS**. ✔️
- **MAIS deux réserves** :
  1. **Redistribution** : `apple-bcm-firmware` **redistribue du firmware Apple extrait de Big Sur**. Le refaire dans une **ISO Eschaton diffusée publiquement** est une **zone grise juridique** (firmware propriétaire Apple). `archiso-t2` l'assume en tant que projet communautaire ; **pour Eschaton c'est une décision à prendre en conscience** (bundle vs script d'extraction au premier boot).
  2. **Régression `wpa_supplicant 2.11`** : Wi-Fi Broadcom cassé depuis cette version ; contournement **`iwd`** (backend) ou désactivation d'offloading. Notre installeur/ISO devrait **utiliser `iwd`** par défaut sur ce matériel. URL : https://wiki.t2linux.org/guides/wifi-bluetooth/
- **Si on choisit de NE PAS bundler** le firmware : l'alternative (script qui télécharge l'image Recovery depuis Apple et extrait) exige **une connexion Internet pendant l'install** — or **le MBP 2019 n'a pas de port Ethernet** (USB-C only). Il faudrait donc **un adaptateur USB-C→Ethernet ou un partage de connexion USB**. Chicken-and-egg réel.

### 5.3 Conséquence installeur (`eschaton-install`)
- Décider **bundle firmware vs extraction** (impact juridique **et** UX réseau).
- Forcer **`iwd`** comme backend Wi-Fi sur Mac T2.
- Bluetooth : firmware idem `apple-bcm-firmware` ; prévenir des glitches BT+Wi-Fi 2,4 GHz.

## 6. Le disque : ce que la T2 change concrètement pour notre partitionnement Btrfs + Limine

### 6.1 NVMe derrière la T2 = disque invisible sans patch
- La T2 **est** le contrôleur NVMe ; le NAND est soudé derrière elle. Sans les correctifs T2 (fusionnés mainline **5.4**, oct. 2019, + pile `apple-bce`), **Linux ne voit pas le SSD interne** — « Linux can't see the internal SSD ». Un installeur générique **ne trouve aucune cible**. Sources : Level1Techs ; Proxmox (Mac mini T2). URLs : https://forum.level1techs.com/t/linux-doesnt-support-t2-as-a-ssd-controller-apples-t2-secure-boot-chip-is-blocking-usage-of-linux-in-t2-chip-macs/134832 · https://forum.proxmox.com/threads/linux-debian-proxmox-ve-installation-on-mac-mini-intel-t2.80442/
- **Donc `eschaton-install` doit tourner depuis un environnement à noyau `linux-t2`** (notre ISO devra être bâtie là-dessus). Une fois le NVMe visible, **partitionner/formater Btrfs/installer Limine se fait normalement**.

### 6.2 Secure Boot : à baisser en Recovery, avant tout
- MBP 2019 = Secure Boot actif. Depuis **macOS Recovery** (`Cmd+R`) → **Startup Security Utility** → Secure Boot **« No Security »** + **« Allow booting from external or removable media »** (indispensable pour amorcer la clé USB). Le réglage **persiste dans la T2/NVRAM** même après effacement du disque → **le faire avant de wiper**. Sources : Apple support 102522 ; TechRepublic ; OSXDaily. URLs : https://support.apple.com/en-us/102522 · https://support.apple.com/guide/security/startup-security-utility-secc7b34e5b5/web
- Un Limine **non signé** boote alors sans souci (No Security = pas de vérification de signature).

### 6.3 FileVault & chiffrement : la T2 chiffre TOUJOURS le SSD
- Sur T2, **le SSD interne est toujours chiffré matériellement** : la Secure Enclave intègre le contrôleur de stockage, « all data between CPU and SSD passes through an encryption stage ». FileVault n'ajoute que la **protection par mot de passe** de la clé de volume. Le volume Data « is always encrypted and can't be run unencrypted ». Sources : Macworld ; eclecticlight.co (2025-01-10). URLs : https://www.macworld.com/article/234494/how-filevault-and-the-t2-security-chip-work-together-in-newer-macs.html · https://eclecticlight.co/2025/01/10/filevault-and-volume-encryption-explained/
- **Conséquences pour Eschaton (analyse)** :
  - Ce chiffrement matériel est **transparent** pour qui pilote le contrôleur : une fois le noyau T2 en place, **Linux voit des blocs NVMe déchiffrés**. On **ne récupère pas** FileVault/APFS pour protéger notre install.
  - **Si on veut du chiffrement au repos pour Eschaton, il faut LUKS/dm-crypt** (pas la T2). *Recommandation nôtre, non fournie par t2linux.*
  - **Si on garde macOS et qu'il a FileVault activé**, prévoir de le **désactiver avant** de redimensionner (`sudo fdesetup disable`), pour éviter les surprises. En **effacement total, FileVault est hors sujet**. Source `fdesetup` : iboysoft.

## 7. Démarrage / Limine sur firmware Apple

### 7.1 Le chemin de repli `/EFI/BOOT/BOOTX64.EFI` = la bonne pratique sur Mac
Le firmware Apple, faute de cible « blessée », charge le **premier `/EFI/BOOT/BOOTX64.EFI`** trouvé. **Limine doit donc s'installer en fallback removable** (équivalent `--removable`), sans dépendre de la NVRAM Apple (capricieuse). Source : matthew-brett docosx ; rEFIt. URL : https://matthew-brett.github.io/docosx/booting_macs.html

### 7.2 Retour d'expérience Limine + Btrfs sur Mac T2 (notre stack exacte : Omarchy)
- **ESP Apple = 300 Mo seulement** → trop petite ; pousse à un `/boot` séparé, ce qui casse les hypothèses de l'installeur.
- **L'installeur Limine réécrit le fallback** : « attempts to overwrite /boot/EFI/Boot/bootx64.efi, breaking my bootloader ».
- **Les scripts systemd-boot (`/boot/loader/entries/`) échouent** : la conf Limine est ailleurs (`/boot/EFI/limine/limine.conf`).
- **Ça finit par marcher** avec des `sed` adaptés (`-linux` → `-linux-t2`, ajout `intel_iommu=on iommu=pt pcie_ports=compat`), et **Omarchy 4.0.0 fonctionnerait « très bien » sur T2 en août 2026** (affichage, trackpad, rétroéclairage, ventilos out-of-the-box). ⚠️ **Rapport communautaire, non reproduit par nous.** Source : discussion Omarchy #773. URL : https://github.com/basecamp/omarchy/discussions/773

**À porter dans SP4b (Limine)** : install fallback maîtrisée ; **ne pas écraser** un `BOOTX64.EFI` préexistant sans confirmation ; ESP à **notre** taille (donc effacement disque) ou `/boot` dédié.

## 8. Double-boot macOS vs effacement total

- **MAJ macOS** : remet le **volume de démarrage par défaut sur macOS** et peut **réinitialiser/toucher l'ESP** ou une `/boot` séparée → boot Linux cassé, à re-« bless ». Reco communautaire : **mettre le bootloader dans l'ESP**, plus facile à restaurer. Sources : ArchWiki *Mac/Troubleshooting* ; forums Mint/eGPU. URL : https://wiki.archlinux.org/title/Mac/Troubleshooting
- **Btrfs + snapper** : indépendant du Mac, fonctionne (stack Omarchy).
- **Recommandation banc d'essai : effacer tout le disque.** Élimine APFS/EFI partagé, MAJ macOS, ESP 300 Mo. Séquence : (1) Recovery → Secure Boot **No Security** + boot externe ; (2) noter que le Wi-Fi firmware est déjà bundlé (§5) donc pas besoin de garder macOS pour ça ; (3) wiper ; (4) installer depuis l'ISO `linux-t2`. **Rappel : pas d'Ethernet sur MBP 2019** → prévoir un adaptateur si besoin réseau pendant l'install.

## 9. Conséquences ISO + doctrine `arch=(any)` + banc d'essai représentatif

### 9.1 Notre ISO
- **Une ISO Eschaton standard ÉCHOUE sur ce Mac** (pas de disque, pas de Wi-Fi). Pour supporter le MBP 2019, il faut **bâtir l'ISO sur `linux-t2`** et y inclure `apple-bcm-firmware`, `apple-t2-audio-config`, `iwd`, `t2fanrd` — c'est **refaire `archiso-t2`**.

### 9.2 Frontal avec « paquets `arch=(any)`, pas de migrations »
- Un **noyau** est `arch=x86_64` (jamais `any`). `linux-t2` vient d'un **dépôt tiers** avec **`SigLevel = Never`**, publié par **un mainteneur unique** au rythme qu'il peut tenir. Chaque bump mainline = **reconstruction + fenêtre de décalage** (§2). C'est l'antithèse de « pas de migrations ».
- **Nuance qui nous aide** : `apple-bcm-firmware` est **`any`** et le firmware est packagé — ça, au moins, colle à la doctrine (au prix du sujet redistribution).
- **Conclusion** : le support **T2 est structurellement hors doctrine**. Ce n'est pas un détail d'empaquetage, c'est un **choix de périmètre produit** à acter en ADR.

### 9.3 Banc d'essai représentatif ? — honnêtement, **NON**
- **Matériel atypique** : firmware Apple, `apple-bce` hors-arbre, Touch ID mort, dGPU AMD à gérer en hybride, veille fragile, ESP 300 Mo, disque derrière la T2. **Rien de tout ça n'existe sur le PC portable/desktop grand public** visé.
- **Risque** : passer des jours sur des bugs **spécifiques Mac** (Touch Bar, `apple-bce`, gpu-switcher) qui **ne servent pas** au public cible, en croyant « durcir le produit ».
- **Usage légitime** : dogfooding de Seylar + validation du **tronc commun** (Limine fallback, Btrfs/snapper, `eschaton-install`, presets) — **à condition de cloisonner le spécifique-Mac**.
- **Formulation honnête à tenir** : « Ce Mac est parfait pour *toi*, mais c'est un mauvais juge de si Eschaton marche *pour les autres*. On l'utilise pour le tronc commun ; on n'en tire aucune conclusion sur le matériel générique. »

---

## 10. Verdict — à vérifier & à prévoir pour SP4b

### 10.1 À confirmer auprès de l'utilisateur (rapide)
1. **Modèle 2019 exact** : 13″, 15″ ou 16″ ? → détermine la **présence du dGPU AMD** (seule vraie variable restante). `Rapport système > Matériel`, ou identifiant `MacBookProXX,Y`.
2. **Intention macOS** : effacer (recommandé) ou cohabiter ?
3. **Accord sur Touch ID** : lui **dire que c'est impossible** et convenir d'un plan B d'auth (clé FIDO2 ? mot de passe graphique ?).
4. **Adaptateur réseau USB-C** dispo pour l'install (pas d'Ethernet natif) ?

### 10.2 Ce que la spec SP4b doit prévoir
- **Décision ADR de périmètre** : T2 = cible officielle, « best effort », ou hors périmètre ? (ma reco : **hors périmètre produit**, toléré pour dogfooding, **cloisonné**).
- **ISO** : variante bâtie sur `linux-t2` **si** on assume T2 ; sinon documenter que l'ISO standard ne s'installe pas sur ce Mac.
- **Bootloader Limine** : install **fallback `/EFI/BOOT/BOOTX64.EFI`**, sans écraser un fallback existant ; ESP dimensionnée par nous.
- **Noyau** : **jamais `linux`** sur cette machine ; épingler `linux-t2` ; **hook de sécurité** empêchant un `-Syu` si `linux-t2` n'est pas prêt pour la version cible ; **snapshot pré-update** + **entrée Limine de secours** + **clé `archiso-t2`** de dépannage.
- **Réseau install** : trancher **bundle firmware `apple-bcm-firmware` (redistribution) vs extraction** ; **`iwd` par défaut** (régression wpa_supplicant 2.11).
- **Chiffrement** : **LUKS** si on veut du repos chiffré (la T2/FileVault n'est pas récupérable côté Linux).
- **Auth** : **abandonner Touch ID** ; concevoir l'auth graphique sur mot de passe et/ou facteur externe FIDO2.
- **dGPU (si 15″/16″)** : prévoir gestion hybride (`apple-gmux`, script switcher) ; tester l'écran noir potentiel.

### 10.3 Incertitudes assumées (2026)
- **Version exacte de `linux-t2` dans `archiso-t2` 2026.03.07** : non affichée (page JS ; « suit le nom du noyau »). Base mainline **7.1.x** confirmée par ailleurs.
- **« Omarchy 4.0.0 marche très bien sur T2 » (août 2026)** : rapport communautaire non reproduit par nous ; à valider sur la machine réelle.
- **Amplitude réelle du décalage `linux-t2` vs mainline** : qualitativement avérée (mainteneur unique, dépôt tiers), **pas chiffrée précisément** dans les sources — à mesurer en conditions réelles avant d'en dépendre pour des updates automatiques.
- **Détail dGPU** dépend du modèle non encore confirmé (§10.1).
